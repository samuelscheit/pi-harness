# Handoff: self-improving Pi harness

Last updated 2026-11-12 (second session). This file is for whoever picks up this work next, a person or an agent.

## Goal

A Pi-based coding harness that runs inside t3 and improves itself over time:

- **Globally** (prompt, extension settings, global skills: this repo) and **per project** (`<repo>/AGENTS.md`, `<repo>/.agents/skills/`, `<repo>/.pi/`).
- **Measured inside the harness**, not from the gateway. The gateway's Usage analytics stay as a legacy view.
- **Evaluated live:** changes are compared across real sessions, not on an offline benchmark.
- **Visible to the user:** every change goes in a changelog with its evidence and measured effect, and can be reverted.

## Current state

### This repo (`~/Developer/Developer/ai/pi-harness`)

- `vendor/pi`: Pi as a squashed git subtree of github.com/earendil-works/pi (9b88b94, after v1.5.2). Update with `git subtree pull --prefix vendor/pi https://github.com/earendil-works/pi.git main --squash`, then re-run the installer. The harness's `node_modules` is a symlink to `vendor/pi/node_modules` (npm can't install the vendored package's dependencies past the user's `before` cutoff).
- Releases and hot reload (`extensions/lib/release.ts`, `extensions/release`): Pi loads the harness from `~/.pi/agent/harness/current`, a snapshot of the latest commit on `main` (without `vendor/`, linked back). A commit is deployed within seconds by any running Pi process, after its extensions pass an import check (a broken commit is reported and skipped), and every session reloads into it when idle. **Uncommitted edits (prompts, experiments, extensions) do not reach sessions: commit to deploy.** Writes (backlog, changelog, experiment stops) go to this repository (`SOURCE_ROOT`); `/harness experiment <name> stop` commits its files. Pi itself (`vendor/pi`) still needs a restart; sessions say so. Go back by pointing `current` at an earlier `releases/<commit>`.
- `prompt/base.md`: the harness's own minimal base prompt (autonomy, `ask_user`, updates during a turn, final answer and file links, skills). It replaced the imported Codex CLI prompt; grow it from evidence when a gap shows up.
- `prompt/AGENTS.md`: the user's global working rules (moved from `~/.claude/CLAUDE.md`).
- `extensions/prompt/index.ts` sets `systemPromptOptions.customPrompt` from `prompt/base.md` and puts `prompt/AGENTS.md` first in `contextFiles`, on every run. Pi still appends the `project_context`, `skills` and `cwd` sections, and sends changed sections mid-session as appended updates.
- `extensions/metrics`: metrics derived from Pi's session files.
    - Pi persists everything needed: the leading system message (prompt sections and tool definitions), later prompt and tool changes, all messages, usage and cost per assistant message, tool `durationMs`, compactions, cache-warm `usage` entries. Nothing is captured live.
    - `indexer.ts` rebuilds each request's context with Pi's `buildSessionContext` (compactions, branches, context edits), `blocks.ts` splits it into blocks in provider order (port of the gateway's `blocks.py`, reading Pi messages instead of provider payloads), `attribution.ts` walks the cache prefix with the rates Pi recorded and explains rebuilds (port of `attribution.py`; a rebuild is ≥ 2k previously cached tokens not read).
    - Harness version = hash of the prompt sections in effect plus the session's initial tools (tools loaded later by tool search are runtime state). Section and tool texts are kept in `blobs` to diff versions. Versions are per project, since `cwd`, `project_context` and `skills` are project sections.
    - `store.ts`: schema in `~/.pi/agent/metrics.db` (10); bumping `SCHEMA_VERSION` drops and re-indexes everything, and Claude Code transcripts are imported again if the store had them (flag in `meta`). Changed files re-index whole; deleted files are pruned. Tool results add what they report (nested calls, `details.changedFiles`, `details.ok`, `details.childSession`); `parent_session` is resolved from Pi's file path to the id.
    - `queries/`: the one query layer. Every function takes a `Scope` (time window on each table's own timestamp, project, source `pi` default | `claude-code` | `all`, model, session) and returns data; `report.ts` renders it as text, the dashboard serves it as JSON. `requests` stores the cost split by billing rate (`cost_input/output/read/write`); `PRAGMA optimize` after each index keeps the planner from scanning every source's requests by time.
    - `/harness stats [all]` (notify) and `npm run metrics -- [--all] [--cwd dir] [--since date] [--until date] [--source s] [--model m]` print the report: totals, cost by content, cache rebuilds, pauses, compactions, tools, versions (with corrections), subagents, context.
    - Usage dashboard (`dashboard/`, modelled on the gateway's Usage area, same components and look): `npm run dashboard` (foreground) or `/harness dashboard` (detached, outlives Pi, log in `~/.pi/agent/dashboard.log`) serves `http://127.0.0.1:4317`. `server/` is node:http (JSON under `/api/`, built frontend otherwise, host-checked); it indexes Pi sessions in a worker on start and on Refresh, Claude Code transcripts once a view asks for that source, and caches responses per URL until the next index. Views: Overview (KPIs vs previous period, findings ranked in dollars, spend by billing rate over time, top sessions), Cost drivers, Context & tools, Sessions + session timeline (compactions, pauses, subagent starts, user messages), Waste, Subagents (new vs resume), Harness versions (per project, with section/tool line diffs). Filters live in the URL. The frontend is rebuilt when its sources changed (`launch.ts`); the installer installs and builds it. Tests: `test/queries.test.ts`, `test/dashboard.test.ts` (seeded store, `test/seed.ts`), `dashboard/src/usage/usage.test.tsx` (vitest; fixtures from `dashboard/scripts/fixtures.ts`), `dashboard/e2e` (Playwright, every view at desktop and phone width against a running server: `DASHBOARD_URL=… npm --prefix dashboard run test:e2e`).
    - The baseline is whatever sessions exist before the first improvement: every past session is in the index.
    - Token efficiency (`efficiency.ts`, inputs from `work.ts`):
        - Subagents: each `delegate_task` call is linked to its child session (the child's first message is a one-line role preamble, a blank line and the `task` verbatim → `sessions.prompt_digest`); `t3_thread_send` calls count as resumes. Per child: cost, wall time, startup write, rediscovery (child calls whose files the parent or an earlier child had already touched) and the estimated cost of resuming the cheapest earlier child instead (its extra context × requests × read rate, + one rewrite if its cache was cold, − startup − rediscovery).
        - Context: request size distribution, tool results whose files were never referenced again (an upper bound for unused context: a later call on the file or the agent naming it counts as use), and per session the best single compaction (keeps 20k + a 3k summary; upper bound, quality not priced).
        - Files per tool call: path arguments exactly, shell commands by path-like words after `cd`, without heredoc bodies and quoted multi-word strings.
        - First numbers (2026-11-12): median request context 144k, p90 362k; best single compactions up to $15 of ~$100; the second gateway subagent was ~$1.35 cheaper new than resuming the warm 128k first one. t3's orchestration section tells the model to always start a new delegate, never `t3_thread_send`; the decision tooling (next) should replace that with these numbers.
- `scripts/install.mjs` (run with the gateway env set, e.g. `zsh -ic 'node scripts/install.mjs'`) builds and globally links `vendor/pi`, removes an npm-installed Pi, and writes to `~/.pi/agent`:
    - `settings.json`: this repo as the only package; default `anthropic/claude-opus-5-5`.
    - `models.json`: the built-in `anthropic` provider routed to the gateway origin with `compat.supportsMessageThreads`, and a `gateway` provider (`openai-responses`) for every non-Claude model from the gateway's `/v1/models`.
    - `auth.json`: both providers read their key with `!security find-generic-password -ws 'pi-harness-gateway'` (Keychain). Needed because t3 starts Pi without shell variables.
- `extensions/ask-user`: `ask_user`, Codex's asynchronous `request_user_input_async` (same description and schema) on Pi dialogs: returns `{"accepted":true}` at once, answers arrive later as an `ask_user` custom message (steer, or a new turn). In t3 each question is a question card that also takes typed text; in the TUI a "Type an answer…" option opens an input.
- `vendor/pi-lens`: pi-lens (github.com/apmantza/pi-lens, MIT, 4.4.12) as a squashed subtree, on trial: LSP, linters, formatters, autofix, read guard, structural rules and its tools (`lens_diagnostics`, `read_symbol`, `symbol_search`, … behind `pi_lens_activate_tools`). The installer builds it (`npm ci --ignore-scripts`, `build:dist`, core grammars; its `prepare` would rewire git hooks) and registers it as the second package. Update with `git subtree pull --prefix vendor/pi-lens https://github.com/apmantza/pi-lens.git master --squash`. Judge it with the metrics: its tools, result sizes and the new harness version per project.
- `extensions/lens`: pi-lens configuration in two layers, every key at both: `config/pi-lens.json` (global, versioned) and `<repo root>/.pi/pi-lens.json` (project). Objects merge, other values replace, `null` removes a global key. The merged file goes to `~/.pi/agent/pi-lens/<hash>.json` and to pi-lens via `PI_LENS_CONFIG_PATH`, set before pi-lens loads (packages load in order). pi-lens's own `.pi-lens.json` (nested rules, ignores) still applies. Global default deviates from pi-lens in one key: `contextInjection.retain: true`, because an injection otherwise rides one request and the next request's prefix differs from the cached one. Verified live: a project file disabling `symbol_search`/`read_symbol` removed both tools.
- A/B experiments (`extensions/lib/experiments.ts`): `prompt/experiments/<name>.md` (frontmatter `status: running|stopped`, `started`, `stopped`; body = the variant). Each session draws an arm per running experiment, 50/50 from sha256(experiment, session id), recorded as a `harness-experiment` custom entry (assignment, forced assignment, or end). `extensions/prompt` adds the body in arm B as its own section `experiment-<name>` (Pi section names allow no `:`). The index keeps `experiment_arms` and `requests.tool_calls` (schema 9); `queries/experiments.ts` compares the arms over random sessions in projects with both arms, counting only turns while the session was in the experiment, with a 95% bootstrap interval of B − A. `/harness experiment [<name> on|off|stop]`. First experiment: `parallel-tools` (the batching rule, moved out of `base.md`; baseline over all Pi turns before it: 0.97 tool calls per turn, 3.9% of turns with 2+). Frontmatter `tools:` switches tools per arm (registered inactive, activated in B by `extensions/prompt`); the comparison then adds the tools' usage, goal rate and rereads, and counts the cost of child sessions a tool ran (`delegations` kind `tool`) in the parent's cost. Tool experiments: `workflow` (`extensions/workflow`: TypeScript scripts run in-process with `tools.*`, `shell`, `llm` (schema answers, session cache), `agent` (child sessions, `files` guard, parallel-safe lock), `map`, `changes`, `sh` (quoted shell commands), a USD budget; saved workflows in `<repo>/.pi/workflows/*.ts` and `workflows/*.ts` become tools; API and model-facing reference in `api.d.ts`), `fix-loop` (the harness workflow `workflows/fix_loop.ts`: a failing check handed to a Sonnet child agent with a short context; green = the check's exit code; changes outside `files` refused or put back), `codemode` (Pi's built-in tool). Setting variants are documented in the module, not built.
- `extensions/improvements`: `note_improvement`, the model's capture of friction for the improvement loop (see Next steps 2).
- `extensions/web`: `web_search` / `web_fetch`. Pi drops server-tool blocks, so each call is its own Messages request (claude-haiku-5-5) with `web_search_20250305` / `web_fetch_20250910` through the gateway passthrough, like Claude Code's WebSearch. Results report their usage (+$0.01 per search); the metrics count it as `tool: <name>` side calls. The 2026 tool versions ran out of tool calls on simple queries through the gateway.
- Vendored Pi patch: `bridgeCacheLookback` in `vendor/pi/packages/ai/src/api/anthropic-messages.ts` (test `anthropic-cache-lookback.test.ts`). - Prompt caching for pauses (vendored Pi, settings written by the installer): `cacheRetention: "long"` (1 h cache, writes at 2x input), `cacheWarmingIdleMinutes: 60` (one idle refresh at ~54 min, so the cache lasts ~2 h after the last request), `compaction.coldCache: { minTokens: 50000, model: "anthropic/claude-haiku-5-5" }` (a run whose cache expired compacts a large context with Haiku first; compaction entries record `reason: "cold"`).
